# АгроМаркет — React + Vite

## О проекте

AgroMarket — frontend маркетплейса сельскохозяйственных товаров. В приложении есть каталог с поиском, корзина и оптовая заявка; пользователи могут зарегистрироваться и войти, а интерфейс учитывает роли и предоставляет формы управления товарами соответствующим ролям.

Frontend построен на React 19 и Vite 8. Он обращается к backend через REST API; публичный адрес API задаётся переменной `VITE_API_URL`. Данные и бизнес-операции обслуживает backend.

## Установка и запуск

Из корня `agromarket-react` установите зависимости и запустите frontend:

```bash
npm ci
npm run dev
```

Откройте `http://localhost:5173`. Backend запускается отдельно; стандартный локальный API-адрес frontend — `http://localhost:3000/api`. При необходимости задайте другой публичный адрес через `VITE_API_URL` до сборки. Не помещайте туда пароли, JWT и другие секреты: значения `VITE_*` попадают в браузерный код. Подробности локального тестового окружения приведены в разделе ЛР12.

## Лабораторная работа 7 — вход, роли и бонусы

### Запуск

Backend должен работать на `http://localhost:3000`, а его PostgreSQL — в Ubuntu
VMware по адресу `<VM_HOST>:5432`. Frontend запускается из этого каталога:

```bash
npm install
npm run dev
```

Откройте `http://localhost:5173`. При необходимости задайте
`VITE_API_URL=http://localhost:3000/api` в локальном `.env`; значение по
умолчанию уже соответствует учебному стенду. Секреты в Vite-переменные не
помещайте: они попадут в браузерный код. Инструкция выше по запуску
`json-server` относится только к исторической ЛР4 и для ЛР7 не нужна.

### Вход и интерфейс

Форма [LoginForm](./src/components/LoginForm.jsx) переключается между входом и
регистрацией. После успешного ответа JWT хранится в `localStorage`, имя
пользователя появляется в шапке, доступна кнопка выхода. После F5 приложение
вызывает `GET /api/auth/me`: недействительный или просроченный токен удаляется,
показывается форма входа. Запросы выполняются через
[apiFetch](./src/api.js), который добавляет Bearer-токен и показывает ошибки API.

Каталог, поиск, счётчик корзины и форма оптовой заявки сохранены. Гость может
отправить заявку без входа. Заявка вошедшего пользователя связывается с его
аккаунтом и появляется в разделе «Мои заявки»; раздел не показывает чужие
заявки. Доступ к данным проверяется на backend, скрытие элементов интерфейса
само по себе защитой не считается.

Администратор дополнительно видит [AddProductForm](./src/components/AddProductForm.jsx),
кнопки удаления товаров и панель заявок. Добавление и удаление обновляют
каталог без перезагрузки. Удаление требует подтверждения. В панели можно
изменить статус заявки; пользователям без роли admin панель не показывается.
Для вошедших пользователей доступна форма смены пароля.

### Четыре бонуса

1. Мои заявки — `GET /api/orders/my` и связь новых заявок с аккаунтом.
2. Удаление товара — подтверждение и `DELETE /api/products/:id` для admin.
3. Смена пароля — форма и `PATCH /api/auth/password`.
4. Панель заявок — просмотр и изменение статуса для admin.

Сообщения 401 завершают сеанс и предлагают войти снова; сообщения 403
показываются рядом с действием. Пароли и JWT не записываются в журнал браузера.

## Лабораторная работа 10 — тестирование

### Запуск проверок

```bash
npm test
npm run coverage
npm run e2e
```

Vitest запускает unit- и component-тесты React в jsdom. React Testing Library проверяет интерфейс через роли и подписи, а mock API/fetch позволяют управлять ответами и проверять ошибки без настоящих запросов.

Playwright запускает E2E-сценарии в браузере. Read-only проверки открывают страницу и каталог. Сценарий регистрации и заказа помечен `@creates-order`: он создаёт пользователя и заявку, поэтому запускайте его только против явно выбранного тестового окружения. Для локального полного сценария укажите `E2E_BASE_URL` тестового frontend, связанного с тестовым API. Не направляйте этот сценарий на production.

### CI и E2E workflow

`React CI` выполняет `npm ci`, `npm run lint`, `npm run test:run` и `npm run build` при push в `main` и при pull request. Отдельный workflow Playwright запускает read-only smoke после успешного deployment, а также по расписанию и вручную. В последних двух случаях адрес берётся из GitHub repository variable `PRODUCTION_URL`. Регистрация, заказы и другие sensitive-сценарии в этот workflow не входят. При ошибке workflow сохраняет smoke-отчёты как artifacts.

### Краткие ответы для защиты

- **Зачем нужны component tests?** Они проверяют поведение отдельных компонентов и быстро локализуют регрессии интерфейса.
- **Зачем mock API?** Он даёт тесту предсказуемые успешные и ошибочные ответы без зависимости от сети, сервера и базы данных.
- **Зачем JWT-тесты?** Они проверяют, что сохранённый токен передаётся в `Authorization: Bearer ...` и защищённый запрос получает правильную авторизацию.
- **Зачем E2E?** Они проверяют ключевые пользовательские действия в работающем браузере и взаимодействие частей приложения.
- **Что показывает coverage?** Какая доля кода была выполнена тестами; высокий процент сам по себе не гарантирует правильность проверок.
- **Зачем CI?** Он автоматически запускает тесты, lint и сборку для изменений и обнаруживает ошибки до слияния.

## Лабораторная работа 11 — безопасность frontend

### Архитектура и интеграция с API

Frontend построен на React 19 и Vite 8 как ESM-приложение. Компоненты каталога,
авторизации, товаров и заказов обращаются к backend через REST API. Общий клиент
`src/api.js` (`apiFetch`) формирует JSON-запросы, добавляет Bearer JWT для
авторизованных операций и преобразует сетевые и HTTP-ошибки в `ApiError`.
Публичный адрес API задаётся через `VITE_API_URL`; если переменная не задана,
используется `http://localhost:3000/api`. Значения `VITE_*` доступны в браузере,
поэтому секреты в них хранить нельзя.

### Общие Zod-схемы и синхронизация

Единственный источник общих схем — `shared/schemas/index.js` в backend-репозитории
`NoName523/agromarket-server`. Frontend синхронизирует именно этот файл по
закреплённому commit SHA `b01cd2adb29e5394e73671dbc2671580a4ea5466` и проверяет
SHA-256 `4A97D7D9345B7CFB2FFDA3B7E557D879EB5230C4575D27E2ED68857C0924176F`.
Скрипт разрешает только заданный репозиторий и путь, не использует fallback на
ветки `main`/`master` и записывает файл лишь после проверки хеша. Полученный
`src/generated/schemas.js` исключён из Git.

`npm run dev`, `npm run build` и `npm test` автоматически запускают
соответствующий lifecycle hook (`predev`, `prebuild`, `pretest`), который
выполняет `npm run schemas:sync` до команды. Отдельный запуск синхронизации:

```bash
npm run schemas:sync
```

Формы входа и регистрации используют `loginSchema` и `registerSchema`, а форма
добавления товара — `productSchema`. Проверка выполняется через `safeParse`; при
ошибке запрос не отправляется, а сообщение схемы показывается у поля. В API
отправляются нормализованные проверенные данные. Backend сохраняет собственную
обязательную проверку и не полагается на клиентскую валидацию.

### Безопасный вывод и обработка ошибок

Название товара выводится обычным JSX text rendering. Пользовательская строка
не интерпретируется как HTML; `dangerouslySetInnerHTML` для такого вывода не
используется. Регрессионный тест `src/components/ProductCard.test.jsx` проверяет
название `<img src=x onerror=alert(1)>`: текст присутствует, внедрённого элемента
с `src="x"` и обработчика `onerror` нет, `alert` не вызывается.

`apiFetch` показывает понятную ошибку при недоступности сервера, некорректном
JSON и неуспешном HTTP-ответе. Формы авторизации и добавления товара отображают
ошибки API, а ошибки валидации — рядом с соответствующими полями.

### Команды разработки и проверок

Команды ниже определены в `package.json` и запускаются из корня frontend-проекта:

```bash
npm ci
npm run dev
npm run lint
npm test
npm run test:watch
npm run coverage
npm run test:coverage
npm run build
npm run e2e
npm run preview
npm run schemas:sync
```

`npm test` запускает Vitest в режиме однократного прогона; `npm run test:watch`
запускает Vitest в watch-режиме. `npm run coverage` и `npm run test:coverage`
выполняют Vitest с покрытием. Playwright E2E запускается командой

регистрации и создания заказа меняет данные, поэтому для него следует выбирать
только явно настроенное тестовое окружение, никогда production.

Команда `npm run build` собирает production-файлы Vite в `dist`. `npm run preview`
предназначена для локального просмотра уже собранного приложения. Фактические
результаты тестов зависят от конкретного запуска и здесь не заявляются.
Lifecycle hook синхронизации настроен для `npm test`, `npm run test:run` и `npm run coverage`.
Команды `test:watch` и `test:coverage` отдельных `pre*` hooks не имеют: в чистом
checkout перед ними сначала выполните `npm run schemas:sync`.

### Пять бонусов ЛР11

1. **Общие Zod-схемы.** Backend хранит единственный исходный модуль, frontend
   загружает его по закреплённому Git SHA и принимает только содержимое с

2. **Защита входа по email.** Backend учитывает неудачные попытки для

   после успешного входа. Frontend показывает полученную ошибку API. Проверка
   механизма выполняется backend unit- и интеграционными тестами; интеграционные
   тесты запускаются только с их безопасной тестовой БД.
3. **Dependabot.** В обоих проектах подготовлены локальные weekly npm-конфигурации
   с раздельными группами обновлений. Для работы обновлений и Security Alerts
   требуется проверить публикацию файлов и включить соответствующие функции в
   настройках GitHub.

### Лабораторная работа 12 — ответы на вопросы

1. **Зачем компонентные тесты и E2E?** Компонентные тесты быстро проверяют отдельные интерфейсы и состояния. E2E проходят ключевой пользовательский путь в настоящем браузере.
2. **Что показывает пирамида тестов?** Чем ниже уровень, тем тесты обычно быстрее и многочисленнее; серверные и клиентские проверки дополняются небольшим набором E2E и smoke.
3. **Зачем Vitest использует jsdom?** Он предоставляет тестам DOM-подобную среду без запуска полноценного браузера.
4. **Для чего React Testing Library?** Проверять интерфейс через доступные пользователю роли, подписи и действия, а не внутреннее устройство компонентов.
5. **Чем отличаются `getBy`, `queryBy` и `findBy`?** `getBy` синхронно требует один элемент; `queryBy` возвращает `null`, если элемента нет; `findBy` ожидает появления элемента асинхронно.
6. **Для чего MSW?** Перехватывать HTTP-запросы и задавать предсказуемые ответы API, включая ошибки, без реального backend.
7. **Зачем `resetHandlers` и очистка `localStorage`?** Возвращать общий тестовый контекст к исходному состоянию и не переносить handlers или сессию между тестами.
8. **Как Playwright auto-wait помогает тестам?** Locator assertions ждут нужного состояния элемента до timeout, уменьшая гонки с рендерингом.
9. **Зачем уникальный email через `Date.now()`?** Повторные регистрации не конфликтуют с записью, оставшейся в тестовой БД.
10. **Что такое smoke и как обезопасить production?** Smoke проверяет минимум критичных страниц. Production-набор ограничен read-only запросами; там нет регистрации и создания/изменения данных.
11. **Что означает HTTP 429 и как проверяется rate limit?** Сервер ограничил частоту запросов; тест проверяет статус и отображение понятной ошибки без обхода ограничения.
12. **Зачем build в CI?** Он подтверждает, что production-сборка создаётся после lint и тестов; локально зелёный результат сам по себе не доказывает успешность CI на GitHub.
13. **Как искать CI-only ошибку и защищать main?** Сверить Node и команды CI, артефакты и логи упавшего job, повторить минимальный сценарий локально. Защитить `main` обязательными checks и изменениями через Pull Request.
